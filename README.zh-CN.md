# FrameLedger

> 一个 Minecraft 客户端模组，用来测量你的帧预算究竟花在了哪里 —— 而不是靠猜哪个图形选项昂贵。

`Fabric` · `Minecraft 1.21 / 1.21.1` · `Java 21` · 独立运行（装不装 Sodium 都可以）

---

## 这个模组为何存在

每个性能模组都会给选项标注性能影响：

```
Performance Impact: HIGH
```

那个标签只是开发者的猜测。它不知道你的 GPU 是什么、你玩什么分辨率、你的世界长什么样。
一个在丛林里要花 4 ms 的设置，在海洋上只花 0.2 ms。
FPS 计数器告诉你"你慢"，但从不告诉你"*什么*慢"。

FrameLedger 回答第二个问题。它把 60 FPS 下约 16.7 ms 的一帧看作一份预算，
对渲染通道进行插桩，然后把这份账本展示给你：

```
GPU frame  11.4 ms
Terrain          8.1  ██████████████████████  71%
Entities         2.0  █████                      18%
Block Entities   0.8  ██                          7%
Sky              0.4  █                           4%
```

于是"调低实体距离"变成了一个背后有数字支撑的决定，而不是猜测。

## 功能

| | |
|---|---|
| **帧预算账本** | 逐通道耗时，覆盖地形、实体、方块实体、粒子、云与天空。 |
| **选项开销实测** | `F10` 对某个原版选项执行交替 A/B 扫描，报告**它在你机器上究竟占多少毫秒**，并给出 95% 置信区间。 |
| **异步测量** | GPU 路径在环形缓冲区中使用 `GL_TIMESTAMP` 查询，结果延迟 3 帧读取，因此性能分析永远不会阻塞它所测量的管线。 |
| **可嵌套的时间跨度** | `GL_TIME_ELAPSED` 无法嵌套；时间戳可以。方块实体在世界通道*内部*计时而不会冲突。 |
| **对数据来源诚实** | 拿不到可信 GPU 路径时回退到 CPU 提交耗时，标注为 `CPU frame`，并在逐通道拆分不稳定时明确警告，而不是假装可信。 |
| **非侵入式** | 不重写渲染器。热路径上只增加计时调用。 |
| **一眼可读** | 行按开销排序，并配有按比例绘制的条形。 |
| **独立** | 装不装 Sodium 都能用。Sodium 是 `recommends`，不是必需。 |

按键：`F8` 账本 · `F9` 展开 · `F10` 测量下一个选项 · 暂停菜单会取消正在进行的测量。

## 为什么不直接用一个自适应画质模组？

自适应模组的做法是对*症状*（FPS 下降）做出反应，去降低设置。那是一个内部含猜测的闭环：
它们不知道是哪个设置导致了下降，于是把所有东西都降级，直到症状消失。

FrameLedger 则产出这些模组所缺少的*归因*信息。两者可以组合使用：用账本找出开销，
用你喜欢的任何方式去处理它。

## 选项开销是怎么测的

对目标选项，模组以 A/B/A/B… 交替分块采样：每块先丢弃开头若干帧让改动生效，
再采样 40 帧，共 8 对。

**为什么交替，而不是"先测完 A 再测 B"：** 相隔数秒的两段数据，差异不止来自那个选项 ——
太阳移动了、怪物刷新了、GPU 可能降频了。交替采样让这类漂移均摊到两组，从而在差值中抵消，
而不是被算到选项头上。

**为什么要置信区间、以及为什么允许"测不出来"：** 小于随机波动的差值只是抛硬币。
当 95% 区间跨过零时，模组会说*"无可测差异"*，而不是印一个换个墙角看就变号的数字。

**哪些选项能测 —— 以及为什么有些不能。** 只测那些立即生效的选项。这一点是读字节码确认的，
不是凭直觉：`ao`（平滑光照）和 `biomeBlendRadius`（生物群系过渡）看起来非常理想，
但它们的变更回调会调用 `WorldRenderer.reload()`。逐帧扫描会把一次多帧的重载卡顿
算进当时生效的那一组，从而得出一个自信的错误答案，所以它们被排除。
目前可测：粒子、云、实体阴影、实体距离、mipmap 等级。

## 经过验证，而非假设

测量基础设施是对着真实运行时验证过的，而不是直接信任：

- 通过导出插桩后的字节码（`-PmixinDebug`）并检查方法体，确认了 Mixin 注入确实生效 ——
  而不是只看一眼"控制台没有报错"。
- Sodium 0.6.13 用 `@Overwrite` 覆盖了 `WorldRenderer.renderLayer`。我们显式检查了在该
  覆盖之下注入是否存活，因为一个静默失效的注入器会一直报告 `0.0 ms` 的地形行，
  看起来却像是"只是没在采样"。
- 在不安装 Sodium 的情况下启动过客户端，确认它确实可以独立运行。
- 用原版绘制顺序核对了计时，并由此发现了一个真实 bug（见下）。

### 由此发现的 bug：地形把实体通道吞掉了

原版 `WorldRenderer.render` 会调用 `renderLayer` **8 次，且不连续**：solid、cutout-mipped、cutout，
然后是实体与方块实体循环，之后才是 translucent、tripwire、translucent、lines、tripwire。

早期版本把一次 pass 计为"从第一次 start 到最后一次 end"。对地形而言，这个区间横跨了整个
世界渲染，于是地形那一行把实体和方块实体也吞了进去 —— 它报告 11.0 ms / 79%，
同时实体又报告了自己的时间，两行互相重叠。现在改为**分段求和**，
这才是"这个 pass 花了多少时间"的真正含义。

### 由此暴露的局限：CPU 的逐通道拆分不可信

在 GL 3.2 上下文下，模组回退到 CPU 提交计时。来自实际会话的六次采样：

| 采样 | Terrain | Sky | 合计 |
|---|---|---|---|
| 2 | 5.43 | 5.31 | 12.15 |
| 3 | 6.59 | 5.64 | 12.97 |
| 4 | 4.48 | 4.17 | 10.50 |
| 5 | 8.36 | 1.77 | 11.93 |
| 6 | 8.23 | 1.64 | 11.53 |

Terrain 与 Sky 朝相反方向移动，而合计保持平稳。这不是可以过滤掉的噪声，而是该后端的固有性质：
CPU 计时测的是**提交**耗时，当驱动阻塞等待 GPU 时，等待会落在当时恰好阻塞的那个调用上。
合计反映真实的等待，而通道之间的拆分并不反映。

因此模组会跟踪每个通道的变异性，在 CPU 后端下打印 `split unstable, total is reliable`
并对相应条形换色，而不是呈递一份无法复现的拆分。逐选项 A/B 扫描不受影响：
它是在同一个通道上交替比较自身，移动的基线会在差值中抵消。

## 构建

```bash
export JAVA_HOME=/path/to/jdk-21   # 需要 JDK 21
./gradlew build              # -> build/libs/frameledger-<version>.jar
./gradlew runClient          # 开发客户端
./gradlew runClient -PmixinDebug   # 额外把插桩后的字节码导出到 run/.mixin.out
```

也可以在 `gradle.properties` 中把 `org.gradle.java.home` 设为 JDK 21 的路径。
`gradle.properties` 固定了 Minecraft、Yarn 与 Fabric API 的版本。

## 使用

1. 把 jar 放入 `mods/`。Sodium 是可选的。
2. 进入世界。首批采样解析完成（几帧）后，账本会出现在左上角。
3. `F8` 隐藏/显示 · `F9` 折叠/展开 · `F10` 测量下一个选项。

一次扫描会让你的设置可见地变化几秒钟，并且**一定会还原**：无论是正常结束、被取消，
还是你退出世界。

### 需要 GL 3.3 上下文

**要求真实上下文版本 ≥ 3.3。** 这一点在开发机上实测踩过坑，值得说明：

Minecraft 在 NVIDIA 驱动上常跑 **GL 3.2 core** 上下文。此时驱动仍会报告
`GL_ARB_timer_query=true`，`glQueryCounter` 函数指针也能解析，甚至单次探针调用会成功，
但在真实渲染中每一次调用都失败。因此本模组**不信任扩展声明**，只认读回来的上下文版本。

在 3.2 上下文下，账本会完全静默并在日志中写一行：

```
GL probe: supported=false ctxVersion=3.2 ... arbTimerQuery=true
GPU timer queries need a GL 3.3 context; ledger disabled for this session
```

这是有意为之：宁可什么都不显示，也不显示假的零值，更不刷 GL 错误。
